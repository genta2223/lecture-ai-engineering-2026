## 演習

- 回答モデル（実行時の`[model]`）：`gemini-3.5-flash-lite`
- 比較した質問：第2回の説明では、LoRAは何を固定し何を学習しますか？ QLoRAは何を加えますか？
- 対象資料（全文投入と他の方式で範囲が違う点も記録）：
  - 検索方式（ベクトル検索・Tree・Graph）は、講義資料DB（第1回〜第3回などのスライド群）から動的に対象ページを取得して参照する。
  - 全文投入（`--full-context`）は、対象資料テキスト全体（227,971文字）を1回のプロンプトに一括で読み込ませて回答する。

- 検索だけを実行して見つかったページと、その本文で確認できたこと：
  - `uv run python -m app.retrieval "LoRA QLoRA 違い"` を実行したところ、1位に第2回 p.52（LoRAとQLoRAの仕組み）、2位に p.51（PEFTの比較）がヒットし、本文および図表の補足文字起こしから「元の重み W は固定、行列 A・B のみ学習」「QLoRAは4bitに圧縮」という根拠を直接確認できた。
- `--trace`で見えたツール呼び出し（ツール名・引数・回数、Treeでたどった目次など）：
  - **全文投入**：ツール呼び出しなし（0回）。最初から全テキストを入力。
  - **ベクトル検索**：`search_materials({'query': 'LoRA QLoRA 固定 学習'})` を1回呼び出し。
  - **Tree**：`browse_tree` を計4回呼び出し（ルート `{}` → `lec02-main` → 章 `lec02-main-s045` → 末端ページ `lec02-main-p052` の順に階層をたどって取得）。
  - **Graph**：`search_graph({'query': 'LoRA 固定 QLoRA 追加'})` を1回呼び出し（上位ページからグラフ接続された周辺ページも一括取得）。
- 取得した情報が足りなかった例、取得できたのに回答へ使えなかった例：
  - 単体検索（`app.retrieval`）では上位5件に p.60（演習）、p.47（RAGとFTの比較）、p.61（演習の進め方）といった同じ第2回内の無関係なページも含まれていたが、エージェントは p.51・p.52 のみを適切に選んで回答に利用していた。
  - Graph 検索や全文投入では、解答に不要な周辺ページや他回のスライドもコンテキストに多く含まれるため、回答に使われない余分な入力トークンが発生していた。
- 今回の用途に採用したい方式と、その理由・比較条件の限界：
  - **採用したい方式**：通常は**ベクトル検索**を基本とし、複数ページをまたぐ概念整理が必要な場合のみ **Graph 検索**を併用したい。
  - **理由**：ベクトル検索は全文投入と比べて入力トークン数を約 1/38（117,025 → 3,027）、APIコストを約 1/27（$0.0357 → $0.0013）に抑えつつ、最も高速（2.39秒）に正確な根拠ページを特定できたため。
  - **比較条件の限界**：今回の比較対象が約23万文字規模の資料であり、質問も特定スライド（p.51-52）に答えが集中する事実確認型だったため、全文投入や Graph 検索の優位性（広範な文脈統合）が表れにくい条件だった。
- 気づき・疑問：
  - Tree 検索は目次構造を人間のように辿れるため透明性が高い反面、階層を降りるたびに LLM の往復（計5回）が発生し、応答時間とトークン数が膨らむトレードオフがあることが分かった。

## 宿題

- 取り組んだレベル：基礎
- やったこと（変更したファイル・設定・処理、または設計した取得方法）：
  - 複数のスライド（p.38, p.39, p.40, p.65）に情報が分散しているテーマについて、同じモデル・同じ資料DBの条件下で「ベクトル検索」と「Graph 検索」の比較実験を実施し、精度・引用網羅性・コストの違いを検証した。
- 比較した質問と、固定した条件（モデル・対象資料など）：
  - **質問**：「コンパクションとセッションをまたぐメモリの違いは何ですか？日々のメモは全部長期メモリになりますか？」
  - **固定条件**：回答モデル `gemini-3.5-flash-lite`、対象資料（講座スライドDB）
- 結果（変更前後の回答・根拠、`--trace`の出力、時間・トークン数・生成API推定費用など）：
  - **ベクトル検索（`search_materials`）**
    - 時間：3.28 秒 / 入力 2,486 tokens / 出力 442 tokens / 応答 2 回 / コスト：$0.001851 USD
    - 引用根拠：第3回 PDF p.39, p.40, p.65（コンパクションと外部保存の違い、OpenClaw の dreaming による選別プロセスを正確に回答）
  - **Graph 検索（`search_graph`）**
    - 時間：3.17 秒 / 入力 5,292 tokens / 出力 419 tokens / 応答 2 回 / コスト：$0.002635 USD
    - 引用根拠：第3回 PDF p.38, p.39, p.40, p.65（ベクトル検索の内容に加え、p.38「すべてを蓄積すると古い情報や誤りも戻るため、何を残し何を消すかを設計する」という設計原則まで補完して回答）
- 改善した例と、残る失敗・制約：
  - **改善した例**：Graph 検索を用いることで、直接のヒットページ（p.39, p.40）に隣接・関連する導入スライド（p.38）の「メモリ設計の原則」まで自動的にコンテキストへ取り込まれ、より背景を含めた網羅的な回答になった。
  - **残る制約**：Graph 検索は周辺ノードを広げる分、入力トークン数がベクトル検索の約 2.1 倍（2,486 → 5,292 tokens）に増加するため、単純な質問に対してはコスト効率が下がる制約がある。
- 気づき・疑問：
  - 検索手法の優劣は単一ではなく、「ピンポイントの事実検索ならベクトル検索」「章全体の背景や前後の文脈・設計思想まで含めて答えさせたい場合は Graph 検索」といったように、質問の性質に応じてコンテキスト取得戦略を使い分けることが重要だと実感した。
